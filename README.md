### Модель в интерфейсе

Редактор/владелец выбирает модель перед отправкой сводки. Начальный список содержит типовые текстовые модели и заданную серверу GEMINI_MODEL. Кнопка «Загрузить список из Google» получает сервером каталог `models.list`, выбирает текстовые Gemini с методом `generateContent` и кеширует его до 15 минут. Ключ остаётся на сервере. Наличие модели в каталоге ещё не гарантирует квоту, доступ к генерации и поддержку всех настроек конкретным проектом. Если каталог не загрузился, текущий выбор сохраняется.

Администратор сервера может ограничить список переменной окружения, например:

```bash
export GEMINI_MODELS='gemini-3.5-flash-lite,gemini-3.8-flash'
```

Если GEMINI_MODELS не задана, можно использовать модель из типового списка или каталога. Выбранная модель фиксируется в записи анализа и истории. У читателя есть просмотр результатов; отправка и загрузка каталога доступны начиная с редактора. Для смены модели в форме перезапуск сервера не требуется.

### Содержательность ответа

Обновлены промпт, схема ответа и входная сводка. Новый ответ должен содержать развёрнутое резюме, общую оценку, предметные выводы с количественными основаниями, интерпретацию, гипотезы и альтернативные объяснения, конкретные действия и приоритетный план P1/P2/P3 с ожидаемым результатом проверки. Вместо общих рекомендаций по отсутствующим данным предлагается прежде всего работа с имеющейся витриной и кодом процедур. Полнота фактического ответа зависит от модели и предоставленных данных.

Добавлены сведения об охвате проверок, продуктовые группы, переходы решений в этих группах и пересечение изменённых путей со сменой решения. Идентификаторы заявок используются локально для расчёта пересечений и не отправляются. Группы пересекаются: их уникальные заявки не суммируются. Совпадение изменения атрибута и решения не объявляется доказанной причиной. Верхняя граница сводки — 75 КБ; лимит ответа для анализа увеличен до 14000 токенов. Короткая команда gemini_client.py --check сохраняет свой небольшой лимит.

Ранее полученные ответы отображаются в прежнем формате. Для нового подробного разбора нажмите отправку ещё раз: новая версия промпта имеет отдельный ключ кеша и создаёт новую запись, не изменяя старую. Повторная отправка той же сводки той же модели и версии промпта переиспользует готовый ответ. Подробные ответы также включаются в отчёт проверок и HTML-экспорт.


## Исправление получения ответа Gemini

Сетевой клиент `gemini_client.py` продолжает использовать потоковое получение и диагностические сообщения. Актуальный порядок обновления страницы и новых модулей приведён в разделе выше.

Теперь ответ принимается потоком SSE через `streamGenerateContent?alt=sse`. Для текстовых Gemini 3 по умолчанию выбран `thinkingLevel=low`, чтобы уменьшить время до начала выдачи. Приложение собирает фрагменты и публикует только полный JSON после `finishReason=STOP` и проверки доказательств. Обрыв, усечение по токенам или незавершённый поток не превращаются в успешный отчёт.

Потоковый режим может сократить период без входящих данных, но не гарантирует устранение разрыва до HTTP-заголовков. Успешные запросы/выходные токены в статистике Google не доказывают, что локальный клиент получил ответ целиком. Корневая причина пользовательского обрыва не установлена: исправлена стратегия получения ответа и добавлена диагностика для следующего запуска.

Короткая проверка на вашей машине (один запрос, использующий API-квоту):

```bash
python3 gemini_client.py --check
```

Используются `GEMINI_API_KEY` и `GEMINI_MODEL` из окружения. Команда не открывает БД, не запускает пользовательские скрипты и не отправляет датасет. Если ответ принят полностью, выводится `OK: ответ Gemini получен полностью и разобран.`

В консоли сервера теперь видны этапы: отправка запроса, получение HTTP-заголовков, первый фрагмент и полное завершение. При ошибке указаны этап, время, число обработанных SSE-событий и байтов. Тексты запросов/ответов, ключи и адреса прокси в журнал не записываются. HTTP-ошибка показывает ограниченное сообщение Google с удалением ключа и URL. Различаются закрытие соединения до ответа, обрыв внутри HTTP, тайм-аут, DNS, TLS, ошибка формата и незавершённая генерация. Автоматических повторов и переключений модели нет: оборванный ответ всё равно мог быть оплачен/учтён Google.

Дополнительные настройки, задаваемые перед запуском сервера:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `GEMINI_RESPONSE_MODE` | `stream` | `stream` — SSE; `single` — прежний `generateContent` для сравнения |
| `GEMINI_THINKING_LEVEL` | `low` для Gemini 3 | `low`, `medium`, `high`; для других моделей по умолчанию не передаётся |
| `GEMINI_TIMEOUT` | `90` | Тайм-аут отдельной сетевой операции в секундах, от 5 до 600; не лимит всей генерации |

Локальные тесты разбора SSE и реального HTTP с chunked-ответом выполняются командой `python -m unittest discover -s tests -p test_gemini_client.py -v`. Эти тесты воспроизводят обрыв соединения и работу нового клиента без обращения к Google. Реальный Gemini остаётся непроверенным в среде разработки: здесь нет настроенного API-ключа.

### Настройка Gemini

Значения задаются в окружении **процесса веб-сервера**, ключ не включается в исходники, не передаётся браузеру или Docker. Модель можно выбрать для каждого анализа в интерфейсе. GEMINI_MODEL задаёт начальное значение; если оно не задано, используется gemini-3.5-flash-lite. Автоматическая смена модели при ошибке и автоматические платные запросы не выполняются.

Linux:

```bash
export GEMINI_API_KEY='ваш-ключ'
export GEMINI_MODEL='имя-доступной-модели'
export DD_PUBLIC_URL='http://192.168.1.10:8765'
python3 app.py --host 0.0.0.0
```

PowerShell:

```powershell
$env:GEMINI_API_KEY = 'ваш-ключ'
$env:GEMINI_MODEL = 'имя-доступной-модели'
$env:DD_PUBLIC_URL = 'http://192.168.1.10:8765'
python app.py --host 0.0.0.0
```

`DD_PUBLIC_URL` — адрес сервера для ссылок в скачанном HTML, например `https://analysis.example.org`. Это корневой адрес без пути. Если не задан, используется `http://Host` текущего запроса; для HTTPS за reverse proxy задайте его явно. Доступ к деталям по ссылкам требует входа и действующих прав.

Откройте завершённое выполнение → Gemini. Сначала можно просмотреть точный JSON, который будет отправлен. Редактор/владелец нажимает «Отправить сводку в Gemini»; читатели видят уже полученный результат. Отправляются итоговые числа, до 80 строк проверок, 30 наиболее затронутых сочетаний пути и типа изменения, до 20 продуктовых групп и пересечения со сменой решения, до 75 КБ. Полные ответы СПР, исходники скриптов и идентификаторы заявок не отправляются. Пользовательские названия и аргументы проверок входят в сводку: перед отправкой проверьте их содержимое.

Запрос идёт асинхронно через `streamGenerateContent?alt=sse` (потоковый режим по умолчанию); сервер ограничивает число параллельных анализов двумя, не повторяет запрос автоматически и переиспользует успешный ответ на ту же сводку/модель/версию промпта. После ошибки повторный запрос к той же модели возможен через 30 секунд. Другая модель выбирается независимо, при общем лимите параллельных анализов. При остановке сервера незавершённый запрос отмечается ошибкой. История хранит автора, модель, время, сводку и результат. Ссылки E1… формирует сервер; выдуманная моделью ссылка отклоняет весь ответ. Наблюдение, гипотеза и действие отображаются отдельно. Последний успешный анализ также включается в отчёт проверок и HTML-экспорт.

Ошибки ключа, прав/региона, квоты, сети, модели, усечённого или неверного JSON отображаются явно. Без ключа и модели раздел показывает причину недоступности; фиктивного аналитического ответа нет. Реальный вызов Google в среде разработки не выполнялся: проверены контракт HTTP и обработка ответов с подменой транспорта.

### Проверки по готовой витрине

Выполнение → «Новые проверки». Выберите доступные проверки и параметры в формате `{ID_проверки: {параметры}}`. Создаётся отдельное выполнение того же прогона: фиксируются текущие версии выбранных проверок, копируется прежняя витрина, контейнер читает её только для чтения. Нормализация, сравнение и агрегация повторно не запускаются. Исходное выполнение и его отчёт сохраняются. Конфигурация самого прогона при этом не меняется.

Производные выполнения независимы от файлов родителя после копирования. Цена этого подхода — дополнительное место: витрина открытого датасета около 385 МБ на выполнение, во время копирования требуется больше. Это осознанное упрощение первой реализации. Логи ссылаются на снимок выполненного скрипта и его текущую карточку. Удаление выполнения/прогона блокируется также на время активного запроса Gemini.

### Точная сводная и детали

Верхняя таблица считает уникальные заявки, объединяя их идентификаторы в каждой ячейке и итогах. Одна заявка может иметь много отличающихся атрибутов, поэтому сумма строк не равна общему числу заявок. BEFORE и AFTER также нельзя суммировать как разные заявки. Нажатие числа сохраняет точные значения измерений, срез, фильтры и исходную страницу сводной. Карточка заявки выделяет выбранный путь/ключ массива и показывает исходный JSON-скаляр: `null`, `false`, `0`, строка и отсутствующий атрибут различаются.

Конструктор WebDataRocks открыт отдельным блоком на той же странице. Его сумма CNT означает **наблюдения атрибутов**, а не уникальные заявки по нескольким путям. Для точного числа и перехода к заявкам используйте основную таблицу. Личные макеты обеих таблиц хранятся отдельно для пользователя и выполнения.

Также загрузчик принимает `RESULTS/BEFORE/*.json` и `RESULTS/AFTER/*.json`, преобразуя названия каталогов к контракту BEFORE_MASTER/AFTER_BETA. При смешении псевдонимов и повторении того же ID/среза загрузка отклоняется.

## Первый запуск

Нужны Python 3.10+ и Docker с поддержкой Linux-контейнеров. На Windows подойдёт Docker Desktop, включённый в режиме Linux containers. На Linux Docker daemon должен быть запущен и доступен пользователю, запускающему сервер.

Для новой установки распакуйте архив в новую папку. При обновлении уже установленной многопользовательской версии 2 следуйте разделу «Обновление существующей установки» ниже. Самая первая одностраничная версия 1 имеет другой формат хранилища; автоматической миграции из неё нет.

Откройте терминал в папке `decision_diff_v2`.

1. Создайте первого администратора и импортируйте открытый датасет/выданные проверки:

```bash
python app.py --create-admin admin --import-demo
```

На Linux при необходимости используйте `python3` вместо `python`. Команда спросит отображаемое имя и пароль дважды. **Готовых паролей нет**. Пароль — от 8 символов. Администратор создаётся только этой локальной командой, обычная регистрация не выдаёт административных прав.

2. Соберите контейнерный образ (при первой сборке нужен интернет для базового образа):

```bash
docker build -t decision-diff-runner:2 -f Dockerfile.runner .
```

3. Запустите веб-сервер:

```bash
python app.py
```

4. Откройте http://127.0.0.1:8765 и войдите под созданным администратором. Выберите «Демонстрационный прогон» → «Новое выполнение».

В Windows можно воспользоваться `setup_windows.bat` для первого шага, затем `build_runner_windows.bat` и `start_windows.bat`.

Без Docker можно пользоваться страницами, регистрацией, загрузкой ресурсов и правами. **Расчёт будет отклонён с понятной ошибкой. Незаметного запуска Python на веб-сервере нет.**

## Редактирование пользователей

Раздел «Мой профиль» позволяет менять отображаемое имя, логин и пароль. Для изменения логина или пароля требуется текущий пароль. Пустой новый пароль означает «не менять». Изменение имени не закрывает сессию. При изменении логина или пароля пользователь входит заново.

Администратор открывает «Администрирование» → «Редактировать» рядом с пользователем. Можно изменить имя, логин, статус, роль участник/администратор и задать новый пароль без знания старого. Для изменения собственного логина/пароля администратор также вводит текущий пароль. Изменение роли, статуса, логина или пароля отзывает прежние сессии этого пользователя.

Нельзя заблокировать себя, снять с себя права администратора или отключить последнего активного администратора. Изменения профиля проверяются на конфликт одновременных правок. Права на ресурсы и авторство привязаны к постоянному ID, поэтому смена имени/логина их не нарушает. Старые подписи в журнале действий сохраняются в том виде, в котором были записаны. Пароли и хеши паролей в аудит не попадают. Пользователи физически не удаляются, чтобы сохранить авторство: для отключения учётной записи используется блокировка.

## Удаление ресурсов и выполнений

На карточках датасетов, скриптов, конфигураций и прогонов владелец или администратор видит «Удалить». Редактору это действие недоступно. У отдельного завершённого выполнения есть своя кнопка удаления.

Обычное удаление перемещает объект в **корзину**. Он исчезает из рабочих списков и выбора ресурсов; прямые ссылки перестают давать доступ. Файлы остаются, поэтому объект можно восстановить вместе с прежними правами. Владелец видит свою корзину, администратор — общую. При восстановлении отдельного выполнения сначала требуется восстановить его родительский прогон, если он тоже в корзине.

Выполняющийся расчёт и содержащий его прогон удалить нельзя. Удаление исходного датасета/скрипта в корзину не удаляет файлы, поэтому не прерывает уже начавшийся расчёт. Новый запуск с такими входами будет заблокирован; в форме выбора отображается недоступный ресурс, а не незаметно подставляется другой.

Из корзины можно **удалить навсегда**: потребуется ввести точное название ресурса или полный ID выполнения. Из рабочего хранилища удаляются все версии файлов датасета/скрипта, либо результаты и входные копии выполнения. Окончательное удаление прогона также удаляет все его выполнения. Записи о ресурсах, версиях и действиях остаются как исторические сведения; восстановление после этого недоступно.

Окончательное удаление входного датасета/скрипта запрещено, пока на него ссылается неполностью удалённая конфигурация, прогон или выполнение. Учитываются **старые версии настроек и корзина**. На странице подтверждения показаны связи, на которые у вас есть права; для недоступных связей предлагается обратиться к владельцу/администратору. Сначала окончательно удалите связанные выполнения/прогоны и конфигурации. Восстанавливаемые объекты не должны потерять свои входные данные.

История действий при удалении не стирается. Удаление исходного скрипта в корзину не меняет результаты старых выполнений; владелец исходника/администратор может открыть его зафиксированную копию из журнала выполнения. Уже скачанные файлы, HTML-отчёты и внешние резервные копии отозвать невозможно. Корзина сама не освобождает место: для этого нужно окончательное удаление. Если ОС не позволила очистить часть файлов, интерфейс сообщает об этом; администратору нужно проверить права каталога хранения.

## Сброс забытого пароля

Остановите веб-сервер (Ctrl+C), откройте терминал в папке существующей установки и выполните:

```bash
python app.py --reset-password admin
```

Вместо admin укажите фактический логин. Введите новый пароль дважды; ввод скрыт. Старый пароль не нужен. Данные, права и результаты сохраняются, прежние сессии этого пользователя закрываются. Команда доступна только через консоль сервера. Если используется DD_STATE, укажите тот же каталог хранения. Затем снова запустите `python app.py`.

## Пользователи

Регистрация создаёт учётную запись в состоянии `pending`. До подтверждения доступна только страница состояния. Администратор открывает «Администрирование», подтверждает заявку. Пользователь входит заново: старые сессии при изменении статуса отзываются.

Администратор также может отклонить или заблокировать участника. Проверка статуса происходит при каждом запросе; блокировка действует и для сохранённых ссылок. Для хакатонной команды отображаемое имя используется как подпись автора, логин — для входа. Это учётная подпись, не электронная цифровая подпись.

## Страницы и навигация

- `/runs` — список доступных прогонов.
- `/runs/new` — создание прогона из конфигурации.
- `/runs/<id>` — настройки, история выполнений, кнопка запуска.
- `/runs/<id>/edit` — изменение настроек через формы выбора ресурсов.
- `/datasets` и `/datasets/new` — список и загрузка датасетов.
- `/datasets/<id>` — карточка и загрузка следующей версии.
- `/scripts` и `/scripts/new` — процедуры/метрики и редактор с загрузкой `.py`.
- `/scripts/<id>` — код (при наличии прав), описание и редактирование.
- `/configurations` — конфигурации обработки; отдельные страницы создания и редактирования.
- `/resources/<id>/access` — настройка доступа.
- `/resources/<id>/history` — версии и журнал действий с авторами.
- `/executions/<id>` — обзор конкретного выполнения, прогресс и журнал.
- `/executions/<id>/pivot` — точная сводная с переносом полей и сохранением вида.
- `/executions/<id>/recheck` — новые проверки по готовой витрине.
- `/executions/<id>/ai` — отправка сводки в Gemini, результаты и история запросов.
- `/executions/<id>/checks` — результаты проверок и экспорт HTML.
- `/executions/<id>/applications` — список заявок выбранной группы.
- `/executions/<id>/applications/<app>` — сравнение заявки.
- `/admin` — подтверждение пользователей и готовность Docker runner.

Это обычные серверные страницы, а не SPA. Фильтры/группировка/пагинация хранятся в URL. Работают обновление страницы, ссылки, новые вкладки и кнопки браузера «Назад/Вперёд». JavaScript нужен только для прогресса, описаний скриптов, извлечения docstring и удобств редактора. Основные формы работают и без него.

## Ресурсы и права

Одинаковая модель применяется к датасетам, скриптам, конфигурациям и прогонам:

- **Личный:** только владелец и администраторы.
- **Поимённый:** указанные пользователи, каждый со своей ролью.
- **Общий:** все подтверждённые пользователи, с общей ролью reader/editor. Индивидуальное назначение может повысить роль.

| Роль | Просмотр | Использование в своём прогоне | Редактирование | Запуск прогона | Управление доступом |
|---|---|---|---|---|---|
| Читатель | Да | Да, если есть права на все выбранные входы | Нет | Нет | Нет |
| Редактор | Да | Да | Да | Да | Нет |
| Владелец | Да | Да | Да | Да | Да |
| Администратор | Все ресурсы | Да | Да | Да | Да |

Запускающий должен быть редактором/владельцем прогона и иметь хотя бы чтение всех используемых датасетов/скриптов. Редактирование общего скрипта для его использования не требуется.

Прямое скачивание исходных датасетов и скриптов для читателей задаётся отдельно: общая галочка или индивидуальное разрешение. Редакторы/владельцы могут скачивать исходники. Сам просмотр результатов прогона не выдаёт прав на скачивание входов и чтение исходного кода процедур. Правила проверяются сервером, включая прямые ссылки и старые версии.

**Существенная граница:** читатель ресурса может использовать его при создании своего прогона; владелец такого прогона имеет право писать и выполнять собственный Python над этими входами. Этот код видит входы целиком и способен включить их в результат. Поэтому запрет кнопки скачивания не является DRM или запретом извлечения данных через вычисления. Не выдавайте доступ к использованию датасета человеку, которому нельзя доверять его содержимое. Это явно отражено на странице настройки доступа.

Доступ к результатам можно предоставлять отдельно: читатель прогона видит отчёты и данные заявок, даже если исходный датасет ему не открыт. Отзыв доступа к прогону закрывает и URL всех его выполнений. Уже скачанный HTML отозвать нельзя.

## Датасеты

Загрузка: ZIP до 64 МБ, распакованный объём до 256 МБ, до 50 000 записей, один JSON не больше 4 МБ. Структура:

```text
RESULTS/
  BEFORE_MASTER/I1001.json
  AFTER_BETA/I1001.json
```

Разрешена внешняя папка перед RESULTS. Файлы вне RESULTS игнорируются, опасные пути и ссылки отклоняются. В обоих срезах должен быть хотя бы один файл, идентификаторы могут не полностью совпадать. JSON должен быть объектом. Имена заявок: латиница, цифры, дефис и подчёркивание.

Загрузка следующего архива через карточку создаёт новую версию датасета. Предыдущие версии и их содержимое сохраняются.

## Скрипты и описания

Для скрипта задаются русское название, описание и назначение: нормализация, сравнение, агрегация, проверка/метрика. Название и описание показываются в форме выбора скриптов.

Можно загрузить `.py` с компьютера или вставить код в редактор. Редактор работает локально, без CDN: подсветка Python, номера строк, Tab/Shift+Tab для одной или нескольких строк, автоматический отступ при Enter, удаление отступа по Backspace и сохранение по Ctrl/Cmd+S. Escape снимает фокус, чтобы выйти из области кода клавиатурой.

Если сервер обнаружил ошибку синтаксиса, отсутствие нужной функции или конфликт версий, он возвращает ту же форму с исходным кодом и заполненными полями, HTTP 422. Не нужно нажимать «Назад», чтобы исправить ошибку.

Черновик дополнительно автоматически сохраняется в sessionStorage текущей вкладки отдельно для пользователя и страницы. Он переживает обновление и возврат на страницу; удаляется автоматически только после подтверждённого сервером сохранения. Если сохранённая версия ресурса изменилась, редактор предлагает явно применить старый черновик к новой версии. Закрытие вкладки/очистка данных браузера может удалить такой черновик — это не серверное хранение и не синхронизация между устройствами. Можно скачать текущий буфер кнопкой «Скачать код .py».

Тип «Проверка / метрика» по умолчанию требует `run(mart, params=None)` и контракт CHECK. Сам по себе произвольный `print(...)` не является подключаемой проверкой. Для остальных назначений нужны функции, указанные в подсказке над редактором. Кнопка «Вставить шаблон» создаёт рабочий пример проверки или заготовку соответствующей процедуры.

Извлечение названия/описания из docstring не требует наличия run: это отдельная операция чтения метаданных. Кнопка «Заполнить из docstring» берёт первую строку начального блока документации как название, остальные — как описание:

```python
"""Проверка снижения одобрений

Отмечает продукты, у которых доля одобренных заявок снизилась.
"""
```

На сервере используется `ast.parse`/`ast.get_docstring`, код для извлечения метаданных **не исполняется**. Если название/описание пусты при сохранении, они также заполняются из docstring. Сохранение проверяет синтаксис и наличие функций контракта. Полная проверка поведения выполняется внутри контейнера.

Каждое сохранение создаёт версию. Если другой участник уже изменил ресурс, сервер откажется затереть его изменения и предложит обновить страницу. Старый код можно открыть через историю. Новый файл не меняет уже выполненные расчёты.

Контракты унаследованы от первой версии:

```python
# Нормализатор
normalize(document, app_id, source, params) -> list[dict]
segments(before, after, app_id, params) -> dict
# Сравнение
compare(union_rows, params) -> Iterable[dict]
# Агрегация
aggregate(rows, segments, params) -> Iterable[dict]
# Проверка / метрика
run(mart, params) -> list[dict]
CHECK = {"id": "custom", "label": "Название", "params": {}, "entrypoint": run}
```

Схемы таблиц и MartAPI — в `docs/` и исходных процедурах. `normalize.py` содержит правила ключей всех массивов. RAW хранит канонический JSON скаляра, поэтому NULL, строка `"NULL"`, false, 0 и отсутствие поля различаются. Сначала строится вертикальный normalized с SOURCE, затем сравнение, разрезы и facts. Исходные пять проверок не изменены.

Для нескольких продуктов одинаковая целевая модель/порог/причина хранится одним значением, разные значения — JSON-картой product_id → значение; PRODUCT_DETAILS сохраняет полные сведения по продуктам. Эту трактовку стоит согласовать с организаторами.

Параметры конфигурации: `normalize_params`, `compare_params`, `aggregate_params`, `check_params`. В `check_params` ключ — ID ресурса проверки (виден в URL её карточки), значение — параметры этой проверки. При запуске имена автоматически сопоставляются с файлами внутри контейнера.

## Прогоны, выполнения, история

При создании прогона настройки конфигурации копируются в него. Изменение исходной конфигурации не меняет прогон автоматически. Настройки самого прогона редактируются на отдельной странице.

Каждый запуск создаёт **новое выполнение**. В нём фиксируются версия настроек прогона, точные версии датасета и скриптов, SHA-256 загруженных файлов, точный ID контейнерного образа и параметры. Используются последние версии доступных ресурсов на момент запуска, затем их копии неизменны. Предыдущий результат не перезаписывается. Повторный расчёт с новой проверкой — новое выполнение, не изменение старого.

История хранит создание, изменения до/после, изменения прав и запуск/завершение расчётов. В каждой записи — автор, отображаемое имя, дата и детали. Автор берётся из сессии, подставить его из формы нельзя. Версии и аудит защищены SQL-триггерами от UPDATE/DELETE. Это защита на уровне приложения/SQLite, не внешняя криптографическая система аудита; администратор файлового сервера управляет самой БД.

## Контейнерный исполнитель

На каждое выполнение создаётся отдельный Linux-контейнер. В него монтируются только:

- выбранная версия датасета, только для чтения;
- зафиксированные копии скриптов и параметры, только для чтения;
- отдельная рабочая папка результатов этого выполнения, с правом записи.

Контейнер не получает базу пользователей, сессии, файлы других выполнений, каталоги ресурсов, Docker socket или переменные окружения сервера.

Настройки запуска: UID/GID 65534, read-only root filesystem, network none, cap-drop ALL, no-new-privileges, память 1 ГБ, CPU 2, до 64 процессов, ограниченный /tmp, до 10 минут. Одновременно допускается два расчёта. Консольный вывод сохраняется до 1 МБ, но поток продолжает вычитываться. Объём файлов результатов проверяется периодически; это не жёсткая файловая квота. При превышении лимита/таймауте контейнер удаляется, выполнение получает failed. Ограничения ресурсов требуют соответствующей поддержки cgroups в Docker-хосте.

После остановки контейнера в каталог отчёта копируются только ожидаемые обычные файлы. Символические ссылки не принимаются. Сервер открывает SQLite только из этого отдельного каталога, в read-only/query-only режиме. Длительность SQL-запросов и объём facts дополнительно ограничены.

Docker-контейнер — практическая изоляция для прототипа, **не гарантия защиты от целенаправленных атак на ядро**. Для публичного исполнения враждебного кода нужен отдельный worker-хост/VM, жёсткие дисковые квоты и дополнительный аудит. На сервере команды также не стоит публиковать встроенный HTTP-сервер напрямую в интернет: для внешнего доступа нужен HTTPS reverse proxy.

Документация используемых опций:
- https://docs.docker.com/engine/containers/run/
- https://docs.docker.com/engine/containers/resource_constraints/

Дополнительные Python-пакеты устанавливает администратор при сборке образа. Интернет во время выполнения отключён. Другой заранее собранный образ можно задать переменной `DD_RUNNER_IMAGE`. Самостоятельной установки пакетов участниками нет.

## Хранение и эксплуатация

- `state/app.sqlite` — пользователи, сессии, ресурсы, права, версии, аудит, список выполнений.
- `state/objects/` — загруженные версии датасетов и кода.
- `state/executions/<id>/input/` — зафиксированные входные процедуры и config.json.
- `state/executions/<id>/artifacts/` — готовая витрина, summary.json, checks.json и журнал.
- `state/executions/<id>/console.log` — ограниченный консольный вывод.

Полный отчёт открытого датасета занимает около 370 МБ, во время обработки и копирования необходимо больше места: предусмотрите не менее 2 ГБ свободного места на расчёт. Удаление из интерфейса поддерживает корзину и окончательную очистку с проверкой связей. Объём резервных копий и корзины контролирует администратор.

Параметры сервера:

```bash
python app.py --host 127.0.0.1 --port 8765
```

`DD_STATE` задаёт другой каталог хранения. `DD_TIMEOUT` — таймаут worker в секундах, по умолчанию 600. Docker build-контекст исключает всё, кроме engine.py и Dockerfile.runner: данные и пользователи не попадают в образ.

Перезапуск страницы не влияет на расчёт. При перезапуске самого сервера незавершённые контейнеры удаляются, выполнения помечаются failed, история сохраняется. Можно создать новое выполнение.

## Проверка

```bash
python -m unittest discover -s tests -v
```

Выполняются тесты сравнения, прав, регистрации/подтверждения/блокировки, CSRF, загрузки файлов, docstring без исполнения кода, версий, конфликта правок, истории, отзывов доступа и отдельных HTTP-страниц.

Один интеграционный тест обрабатывает **доверенные выданные процедуры** напрямую в тестовой среде и проверяет отчёты всего датасета. Это специальная тестовая фикстура; сервер не предоставляет такого режима исполнения.

Реальная проверка контейнера включается отдельно после сборки образа:

Linux:
```bash
DD_TEST_DOCKER=1 python -m unittest discover -s tests -p test_docker_runtime.py -v
```

PowerShell:
```powershell
$env:DD_TEST_DOCKER="1"
python -m unittest discover -s tests -p test_docker_runtime.py -v
```

## Границы готовности этой версии

- В среде разработки Docker отсутствует. Построение команды и отказ без контейнера проверены автоматически, **реальный запуск Docker здесь не проверен**. Для него включён отдельный тест выше.
- В Chromium выполнен браузерный проход: drag-and-drop, сохранение личного вида, WebDataRocks, выбранный атрибут, Gemini с подменой HTTP-транспорта, отчёт и сохранение кода после ошибки. Ошибок JavaScript и внешних сетевых обращений интерфейса не обнаружено. Firefox/Windows не проверялись. Регрессии редактора: `node tests/test_editor.js`. Node нужен только для тестов, не для приложения.
- Нет ячеек Jupyter, сравнения двух выполнений между собой, переноса владельца, восстановления пароля по электронной почте, автоматической очистки корзины и миграции хранилища первой версии. Gemini подключён; реальный ответ API требует настройки ключа и модели на сервере.
- Обработка новых порций данных до завершения прогона не реализована.
- Точная сводная поддерживает перенос полей между строками (1–4) и столбцами (до 2), фильтры и сохранение личного вида. Вывод: до 100 строк и 12 столбцов за страницу. Дополнительный WebDataRocks работает с суммой наблюдений атрибутов, имеет собственный конструктор полей/фильтров и ограничение объёма данных 1 МБ; при превышении нужен более узкий фильтр. Число уникальных заявок вычисляет основная сводная объединением идентификаторов.
- Первый результат на открытом датасете: 2002 заявки, 289533 атрибута сравнения, 502 заявки с различиями, 385 смен решений. С закрытым эталоном организаторов не сверялся.
