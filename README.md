## Быстрый старт

Нужен Python 3.10+. Сторонних Python-пакетов нет. Команды выполняются из корня репозитория (на Linux/macOS — `python3` вместо `python`).

```bash
# 1. Создать администратора и загрузить открытый датасет (спросит имя и пароль)
python app.py --create-admin admin --import-demo

# 2а. Штатный запуск: процедуры выполняются в изолированном Docker-контейнере
docker build -t decision-diff-runner:2 -f Dockerfile.runner .
python app.py

# 2б. Без Docker (демо на одном компьютере, только 127.0.0.1)
python app.py --local-runner
```

Откройте http://127.0.0.1:8765 → «Прогоны» → «Демонстрационный прогон» → «Новое выполнение». Через 15–25 секунд на обзоре появится итог: **385 из 2 002 заявок сменили решение**, различия в ответе есть у **502**.

На Windows те же шаги выполняют скрипты `setup_windows.bat`, `build_runner_windows.bat` и `start_windows.bat` (или `start_windows_local.bat` без Docker).

## 1. Описание решения

Перед выкатом правки стратегии одни и те же заявки прогоняются через версию с прода (BEFORE, MASTER) и через новую версию (AFTER, BETA). Ответ СПР по одной заявке — это документ из 131–178 атрибутов. Decision Diff превращает два среза таких ответов в отчёт, по которому аналитик за минуту отвечает на четыре вопроса:

- **Сколько заявок изменилось и у скольких сменилось решение.** На обзоре выполнения — одна фраза-итог и полоса распределения переходов: «Одобрено → Отказ», «Отказ → Одобрено» и т. д.
- **Из-за чего сменилось решение.** Блок «Почему сменилось решение» относит каждую смену к рычагу стратегии: сдвиг порога, другой балл или модель, снятый или новый стоп-фактор. У каждой причины есть ссылка на её заявки.
- **Какие атрибуты меняются чаще всего и кого это затронуло.** Сводная таблица с изменяемой раскладкой считает уникальные заявки. От любого числа можно перейти к списку заявок, затем к заявке и к конкретному атрибуту «до/после».
- **Где различия есть, а решение не изменилось.** Для этого есть отдельная проверка и строка на обзоре.

**Реализованный функционал:**

- Многопользовательская работа: регистрация с подтверждением администратором, роли (владелец, редактор, читатель), доступ к ресурсам (личный, поимённый, общий), история версий, журнал действий, корзина.
- Ресурсы: датасеты (ZIP с ответами), процедуры (нормализация, сравнение, агрегация), проверки, конфигурации, прогоны. Процедуры и проверки подключаются либо загрузкой `.py`, либо кодом во встроенном редакторе с подсветкой Python.
- Запуск расчёта в фоне с прогрессом и журналом этапов. У каждого этапа есть ссылка на зафиксированную версию его кода и на вывод Python.
- Отчёт проверок — единая таблица PASS/FAIL. Бледные строки — мало данных, уверенности в проблеме нет. Ссылки ведут к заявкам. Отчёт скачивается в HTML, а из файла можно перейти в сводную приложения.
- «Новые проверки» по готовой витрине — без повторной обработки JSON.
- Качество входных данных: отсутствующий, повреждённый или не-UTF-8 ответ исключает заявку целиком. Причины видны в отчёте, а строки «Ошибки исполнения BEFORE/AFTER» добавляются автоматически.
- Второе мнение языковой модели (Gemini) по агрегатам и результатам проверок. Работает при заданном `GEMINI_API_KEY`.
- Русский интерфейс с понятными названиями атрибутов, светлая и тёмная тема. Работает без интернета.

## 3. Используемые технологии

- **Python 3.10+, только стандартная библиотека:** `http.server`, `sqlite3`, `json`, `zipfile`, `subprocess`, `threading`. Зависимостей нет, поэтому развёртывание сводится к одной команде.
- **SQLite** — база приложения и витрина каждого выполнения (отдельный файл `mart.sqlite`).
- **Docker** — изоляция пользовательского Python: без сети, файловая система только для чтения, непривилегированный пользователь, лимиты CPU, памяти и процессов.
- **Серверный HTML и немного JavaScript** без фреймворков: страницы работают и без JS, ссылки сохраняют историю браузера.
- **WebDataRocks 1.4.23** — дополнительный конструктор сводной с русской локализацией, включён в репозиторий.
- **Gemini API** (REST, потоковый SSE) — второе мнение модели. Ключ хранится только на сервере.
- **Шрифты Onest и JetBrains Mono** (лицензия SIL OFL) лежат в проекте, поэтому интернет не нужен.

## 4. Данные

Используется только выданный датасет `data/RUN-20260827-0001`: 2 002 заявки, по одному JSON-ответу в `RESULTS/BEFORE_MASTER` и `RESULTS/AFTER_BETA`, имя файла — идентификатор заявки. Дополнительных данных нет.

Предобработка выполняется процедурой нормализации и описана в разделе 5. Команда `--import-demo` копирует датасет в хранилище приложения. Свой датасет загружается через интерфейс ZIP-архивом (до 64 МБ) со структурой `RESULTS/BEFORE_MASTER/*.json` и `RESULTS/AFTER_BETA/*.json`. Повреждённые и неполные ответы сохраняются для диагностики.

## 5. Архитектура и подход

```
Браузер ──HTTP──► app.py ──► store.py (SQLite: пользователи, ресурсы, версии, права, аудит)
                    │
                    ├─ «Новое выполнение»: service.py фиксирует снимок конфигурации и кода
                    │        └─► sandbox.py ──► Docker (или --local-runner) ──► engine.py
                    │                                   ├─ чтение и валидация JSON
                    │                                   ├─ normalize → вертикальная витрина (SOURCE)
                    │                                   ├─ compare  → сравнение, 4 типа изменений
                    │                                   ├─ aggregate → факты counts + APP_IDS
                    │                                   └─ checks   → строки PASS/FAIL
                    │        ◄── mart.sqlite, summary.json, checks.json, status.json
                    │
                    └─ отчёты читают витрину только на чтение: обзор, сводная, проверки, заявки, HTML
```

**Этапы расчёта** (`engine.py`, по заявкам, без загрузки всего датасета в память):

1. **Чтение и валидация.** Каждый ответ проверяется отдельно: отсутствие файла, кодировка UTF-8, корректный JSON, повторяющиеся ключи, NaN/Infinity, верхний уровень — объект. Если хотя бы один ответ заявки некорректен, вся пара исключается из сравнения, а причина пишется в таблицу `input_status`.
2. **Нормализация** (`procedures/normalize.py`). Документ превращается в плоские строки базового формата: `APP_ID, SOURCE, PREFIX, CLASS, SUFFIX, KEY, ARRAY_KEY, PATH, RAW, VALUE_ADJUSTED`. Элементы массивов сопоставляются не по позиции, а по ключу: продукт по `product_id`, правило по `name`, модель по `modelName`, оффер по `product_id` и `type`. Это три режима сравнения массивов из `docs/ФОРМАТ_ОТВЕТА.md`: по ключу, по значению, по индексу. Технические поля (`request_id`, `createDateTime`) исключаются. Числа дополнительно раскладываются в бакеты (`VALUE_ADJUSTED`) для сводной.
3. **Вертикальная витрина.** Строки BEFORE и AFTER хранятся в одной таблице `normalized`, а срез задаётся полем `SOURCE`, как требует задание. Горизонтальное представление «до / после» строится только в интерфейсе карточки заявки.
4. **Сравнение** (`procedures/compare.py`). Пары сопоставляются по `APP_ID + PATH + ARRAY_KEY`. Тип изменения — один из четырёх: `VALUE_CHANGED` (значение изменилось), `ATTRIBUTE_NEW` (появился), `ATTRIBUTE_LOST` (исчез), `SAME` (без изменений). Значения сравниваются как канонический JSON, поэтому `null`, `false`, `0` и пустая строка различаются.
5. **Агрегация** (`procedures/aggregate.py`). Сравнение группируется по измерениям отчёта (путь, тип изменения, срез, бакет, элемент массива), и для каждой группы считается число уникальных заявок со списком их идентификаторов. Эти факты питают сводную и переход к заявкам.
6. **Проверки** (`checks/*.py`). Каждая проверка получает API витрины (`mart.rows`, `mart.app_ids`, `mart.segments`…) и возвращает строки `LABEL, SOURCE, ARGUMENT, CNT, TOTAL, METRIC, APP_IDS, RESULT, CONFIDENCE`. Приложение объединяет их в единый отчёт.

**Ключевые технические решения:**

- **Расчёт — в отдельном процессе, отчёты — по готовой витрине.** Пока идёт приведение данных, веб-сервер отвечает, а страница выполнения показывает прогресс и этапы. Отчёт открывается только после полного завершения; частичных результатов нет.
- **Пользовательский код изолирован.** Процедуры и проверки — это произвольный Python, поэтому по умолчанию они выполняются в контейнере без сети и без доступа к базе приложения. Без Docker расчёт запрещён. Исключение — явный демо-режим `--local-runner`, который разрешён только на 127.0.0.1.
- **Воспроизводимость.** При запуске фиксируются версии и SHA-256 датасета и каждого скрипта. Журнал этапов ведёт к той версии кода, которая реально исполнялась, а не к текущей.
- **Точная сводная по уникальным заявкам.** В ячейках объединяются множества `APP_ID`, а не суммируются счётчики, поэтому одна заявка с десятком изменённых атрибутов учитывается один раз.
- **Формат ответа — в процедурах, а не в приложении.** Чтобы поддержать другой тип ответа, достаточно поправить процедуру нормализации или добавить поле контекста. Код приложения менять не нужно.
- **Модель — второе мнение, а не замена проверкам.** Витрина целиком в модель не помещается, поэтому в Gemini уходит сжатая сводка до 75 КБ: итоговые числа, переходы решений, до 80 строк проверок, наиболее затронутые сочетания «путь × тип изменения» и продуктовые группы. Полные ответы СПР, код и идентификаторы заявок не отправляются. Каждый вывод модели должен ссылаться на элементы этой сводки, и ссылки проверяются.

## 6. Эксперименты и результаты

**Результаты на открытом датасете:**

| Показатель | Значение |
|---|---:|
| Заявок во входных данных / сопоставлено / исключено | 2 002 / 2 002 / 0 |
| Заявок с различиями | **502** |
| Заявок со сменой решения | **385** |
| Строк сравнения | 289 533 |
| Нормализованных строк (BEFORE + AFTER) | 572 221 |
| Атрибутов: изменилось / появилось / исчезло | 7 567 / 3 835 / 3 010 |

Числа 502 и 385 сверены с независимым пересчётом по сырым JSON без процедур приложения.

**Что изменилось в решениях:**

| Причина | Заявок | Переход |
|---|---:|---|
| Порог cutOff сдвинут 0,55 → 0,62 / 0,70 вместе со сменой скоринга | 217 | Одобрено → Отказ |
| Снят стоп-фактор AGELOW@21 | 112 | Отказ → Одобрено |
| Новый стоп-фактор DOCS_EXPIRED | 56 | Одобрено → Отказ |
| Различия есть, решение прежнее | 117 | — |

**Проверенные гипотезы и выбранный подход:**

- *Сравнение массивов по позиции* давало ложные изменения, когда продукты или правила меняли порядок. Выбрано сопоставление по ключу элемента, а число 502 совпало с проверкой, не зависящей от порядка.
- *Неполные пары как «атрибут появился/исчез»* засоряли сводную ложными изменениями. Выбрано исключение пары целиком до сравнения, а настоящие появления и исчезновения внутри корректных пар считаются как обычно.
- *Сумма счётчиков в сводной* завышала число заявок. Выбрано объединение множеств идентификаторов.
- *Пять выданных проверок* не показывали два из трёх главных рычагов изменения. Добавлены проверки «Порог сдвинулся», «Стоп-фактор новый», «Различия есть, решение то же» и автоматические «Ошибки исполнения».

**Производительность** (один прогон на хосте, без лимитов контейнера):

| Операция | Время |
|---|---:|
| Полный расчёт 2 002 заявок | 15–25 с |
| Открытие сводной (первое / повторное) | 0,26 / 0,03 с |
| Смена раскладки / фильтр | 0,02 / 0,01 с |
| Список заявок / карточка заявки | 0,25 / 0,005 с |
| «Новые проверки» по готовой витрине | ≈ 0,5 с |

**Тесты:** 85 автотестов (`python -m unittest discover -s tests -p "test_*.py"`). Они покрывают движок, сравнение, качество входных данных, права доступа, HTTP-страницы, редактор, Gemini (тестовый транспорт), новые проверки и блокировки файлов в Windows. Подробности — в [tests/VALIDATION.md](tests/VALIDATION.md).

**Подготовка данных:** не требуется — открытый датасет уже лежит в `data/`. Его загружает команда `--import-demo`. Свой датасет загружается через «Датасеты» → «Загрузить» в виде ZIP-архива.

cd B_Beatiful
python app.py --create-admin admin --import-demo      # имя и пароль (от 8 символов)
docker build -t decision-diff-runner:2 -f Dockerfile.runner .

**Воспроизведение результатов:** «Прогоны» → «Демонстрационный прогон» → «Новое выполнение». Ожидаемо: 502 заявки с различиями и 385 со сменой решения. Затем можно открыть вкладки «Сводная», «Проверки», «Заявки» или скачать отчёт в HTML.

## 8. Ограничения и развитие

- **Нет потоковой обработки.** Расчёт начинается после загрузки всего датасета; приём ответов по мере их поступления (необязательный пункт задания) не реализован.
- **Один сервер.** Веб-сервер и координатор расчётов работают в одном процессе, одновременно идёт не больше двух расчётов. Для 20 000+ заявок и многих пользователей следующий шаг — очередь задач и отдельные воркеры.
- **Размер витрины** около 385 МБ на 2 002 заявки, а «Новые проверки» копируют витрину родителя. Направление развития — ссылка на витрину вместо копии и колоночное хранилище (DuckDB/Parquet).
- **Конструктор WebDataRocks** ограничен 1 МБ данных, при большем объёме нужно сузить фильтры. Основная точная сводная этого ограничения не имеет.
- **Gemini** работает только с ключом API; без ключа раздел честно сообщает о недоступности.
- **Локальный режим** `--local-runner` выполняет код процедур без изоляции и предназначен только для показа на одном компьютере.
- **Windows и OneDrive.** Папку `state` лучше держать вне синхронизируемых папок (`DD_STATE`): витрины крупные, а синхронизация может временно блокировать файлы.
